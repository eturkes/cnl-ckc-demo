# u10b — a rejected `ask()` settles into a terminal state

Tier: `kernel`. The run lifecycle is the only path between a selected question and a rendered
Prolog answer, and no downstream lane re-checks it for free — `browser:check` drives the happy
path and cancel alone, `smoke` drives one answer. Rigor concentrates here.

Dispatch: `test-u10b` (diff-blind red suite from P1-P7) + `orc-u10b` (independent transition
model as a differential oracle); MAIN authors the controller fix.

## The defect

`DemoController.#start` builds `done = query.then(onSettle, onReject)`. `onReject`
(`DemoController.svelte.ts:224-226` at base) retires the active run and rethrows, leaving the
`{ kind: 'running' }` written at `:201` in place. `App.svelte:151` calls `void demo.run()`, so
the rejection reaches nothing: the browser logs an unhandled rejection, the answer region keeps
`aria-busy="true"`, the busy status copy stays, Retry stays hidden and Cancel stays enabled
while being a no-op — `cancel()` reads the already-cleared `#active` and returns at `:146`
before it can abort or write `cancelling`.

The rejection is reachable. `EngineClient.query` resolves every named failure rather than
throwing (`#send` catches the disposed-client throw at `client.ts:169-173` and resolves
`error/protocol`), but `DemoEngine.ask` is an injected interface: `AnswerService.ask` has no
catch around its awaited query (`service.ts:46`), so any rejected engine promise propagates as
an arbitrary `unknown` value.

## Predicates

Each is a `tests/demo-controller.dom.test.ts` case driving the real `App` through the injected
`ViewEngine`, except P5 which may drive `DemoController` directly.

- **P1 terminal state.** After a run whose `ask()` rejects, `controller.state.kind` is
  `'settled'` and `state.result.kind` is `'error'`. The carried `EngineError.code` is `worker`
  and its `message` is the rejection reason's text — `cause instanceof Error ? cause.message :
  String(cause)`, which is what `#boot` and `#trace` already do with an unexpected rejection.
- **P2 no rejection escapes.** The promise returned by `run()` fulfils. A test that awaits it
  without a `catch` passes, and no `unhandledrejection` is raised.
- **P3 the view is not busy.** The answer region reports `aria-busy="false"`, the Cancel
  control is disabled, and Retry is present — the same rendering `settled/error` already gets
  from `describe.ts:96-100`.
- **P4 the failure is announced.** The rendered error text is `TEXT.runFailed(code, message)`
  and the summary is `TEXT.runFailedSummary()`, in an element an assistive technology reads.
  No new copy key: `en.ts:256` and `ja.ts:230` already carry both.
- **P5 no poisoning.** A run started after a rejected run dispatches its own `ask()` and
  settles on its own result. At base `query = previous.query.then(dispatch)` propagates the
  predecessor's rejection, so `dispatch` never runs and the successor inherits the failure.
- **P6 a superseded rejection writes nothing.** When run A is superseded by run B and A's
  `ask()` then rejects, the state stays B's. The rejection arm must carry the same
  `this.#active?.controller !== controller` ownership guard the fulfilment arm has at `:216`.
- **P7 cancel after a rejection is inert.** `cancel()` called once the rejected run has
  settled fulfils and leaves `state.kind === 'settled'` — it never regresses to `cancelling`.

## What the oracle found that the contract did not

O4 and P5 converge on one root cause the defect statement missed. `query =
previous.query.then(dispatch)` propagates a predecessor's rejection, so a rejected run does
not merely strand itself — it cancels its SUCCESSOR's engine call and then retires the
successor's own run record, leaving `cancel()` inert on a run that never dispatched. The fix
is `.then(dispatch, dispatch)`: the predecessor's outcome decides when this run dispatches,
never whether.
