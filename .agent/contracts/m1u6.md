# m1u6 — run lifecycle + answer states

Base `5e3bf46`. tier `kernel`. Spine: a selected catalog question becomes a live
Prolog run whose every typed outcome renders, announces and cancels honestly.

Wave 1 inputs: `.scratch/agents/map-m1u6.md` (25/25), `spike-m1u6-handle.md`
(10/10), `spike-m1u6-signal.md` (10/10). Evidence branches
`wt/spike-m1u6-handle` (`b896d2e`) and `wt/spike-m1u6-signal` (`3066404`);
`map-m1u6` delivered its report alone and left `wt/map-m1u6` at the base.

## Decisions

**D1 — cancellation surface = trailing optional `AbortSignal`.** Both spikes
built a working cooperative cancel and both closed `fail(med)` on the same
defect: run ownership is convention, not type. The discriminators are therefore
surface and blast radius, where alt B wins — 3 files / +507 −5 / **0 existing
tests changed**, against alt A's 4 files / +569 −71 / 1 existing test changed.
Alt B also keeps `EngineClient`'s correlation id private, which is the invariant
that created the problem, and leaves `QueryOutcome` and `AnswerResult` exactly as
u2 and u4 shipped them. Cancel latency does not discriminate: 1.869 ms median
(alt B) against 0.355 ms (alt A), both far below the cooperative
granularity that bounds when a cancel can land at all.

**D2 — one Prolog iterator at a time.** `EngineSession` holds a single `#active`
query and an abandoned iterator poisons every later query (u3: 8 cascading
`failure`s). A replacement run therefore aborts its predecessor, becomes visible
immediately, and issues its own engine call only after the predecessor settles.
Visible-state latency and engine serialization are separate concerns.

**D3 — identity guard on every state write.** Both spikes' P10 is the same
defect class: an unguarded controller lets a retired run's late result overwrite
the active one. Every controller state write is gated on the run's own
`AbortController` still being the active one.

**D4 — retry mints a fresh `AbortController`.** An aborted signal is permanently
aborted, so a reused one cancels the next run before the worker is created
(`spike-m1u6-signal` P5: `reused_posts=0 fresh_spawns=0`).

**D5 — `DEMO_BUDGET` is frozen and controller-owned.** `BUDGET_MAX` is a
ceiling, not a default; shipping it would put a ten-minute clock behind a demo
button. Values are corpus-measured, ten trials per catalog id against the real
generated PVM (map S6): observed maximum 119.972 ms, all 60 runs `solutions`.
`wallClockMs` is set at 5000, not the probe's 2000, because the deadline is the
one budget whose over-tightening produces a *dishonest* answer — a false `limit`
where a proof exists — while over-loosening only delays a run the user can
cancel. The browser PVM boot floor is 335 ms and browser WASM is slower than the
Node measurement, so 41× headroom over the Node maximum is the honest setting.

**D6 — one `role="status"` and one `role="alert"`, both mounted from first
render, never mirroring each other.** ARIA22 requires the live region to pre-exist
its update; two sources for one message announce it twice.

**D7 — answer selection = native radio group.** One-of-N is the APG Radio Group
pattern. Native `<input type="radio">` inside `<fieldset><legend>` supplies the
group relationship, checked state, single tab stop, Space and wrapping arrows for
free, and dodges the `svelte-check` a11y warnings that a custom clickable card
raises (map S12).

**D8 — native `<button type="button">` with native `disabled`.**
`aria-disabled` communicates state without blocking activation; nothing here
needs a focusable disabled control.

**D9 — no focus steal.** Announcement carries every async transition. Focus moves
only when the control holding it becomes unusable: Cancel → Retry after an error,
otherwise Cancel → Run.

**D10 — layout.** `src/demo/DemoController.svelte.ts` (rune-bearing, so `.svelte.ts`),
`src/demo/RunControls.svelte` (buttons + status + alert),
`src/demo/AnswerPanel.svelte` (answer states + radio group), `src/App.svelte`
composes. Suite `tests/demo-controller.dom.test.ts` joins the existing `dom`
project on its glob alone; `tests/engine-cancel.test.ts` joins `node`.

## Predicates

### C — cancellation surface

- C1 `EngineClient.query(goal, budget, signal?)`: trailing optional; every
  existing two-argument call compiles and behaves unchanged.
- C2 `AnswerService.ask(id, budget, signal?)`: trailing optional; the id-only
  guarantee holds — free text, an unknown id and a raw goal each return
  `rejected` and post zero engine requests.
- C3 Aborting a live query settles that caller `cancelled`, carrying the
  solutions already proven.
- C4 One abort posts exactly one `cancel` request targeting that query's id; a
  second abort on the same signal posts none.
- C5 A pre-aborted signal settles `cancelled` without spawning a worker and
  without posting a query.
- C6 Settlement removes the abort listener: an abort after settle posts nothing
  and produces no unhandled rejection.
- C7 A hard reset during signal-bound live queries settles every caller exactly
  once, and no late response from the retired generation claims a request.

### R — run lifecycle

- R1 The controller owns one `EngineClient` and one `AnswerService`; a boot
  failure becomes a typed error state, never a rejected promise reaching a
  template.
- R2 Selecting a question records the selection and starts no run.
- R3 `run()` enters `running` synchronously and reaches the settled state
  carrying the `AnswerResult`.
- R4 Starting a run while one is live aborts the predecessor and issues the new
  engine call only after the predecessor settles: overlapping engine queries = 0.
- R5 A retired run's late result never replaces the active run's state.
- R6 `cancel()` aborts the active run, enters `cancelled`, and awaits that run's
  settlement.
- R7 `retry()` runs the same catalog id under a fresh `AbortController`; it never
  reuses an aborted signal.
- R8 `dispose()` aborts the active run and disposes the client; no state write
  follows.
- R9 `DEMO_BUDGET` is frozen and is the only budget the controller passes; the
  controller exposes neither a goal nor `consult`.
- R10 Against the real PVM all six catalog ids settle `answer` under
  `DEMO_BUDGET` with counts 7 / 5 / 2 / 1 / 3 / 12.

### V — view and accessibility

- V1 Exactly one `role="status"` node, present at first render, never focused.
- V2 Exactly one `role="alert"` node, present at first render; error text appears
  there alone and is not mirrored into the status node.
- V3 Ten states each render their own visible text label, none distinguished by
  colour or icon alone: `booting`, `boot-error`, `idle`, `running`, `cancelling`,
  and `settled` split by `result.kind` into `answer`, `failure`, `limit`,
  `cancelled` and `error`.
- V4 `limit` names its `LimitKind`, labels retained solutions as partial, and
  never reads as "no answers" merely because none were retained.
- V5 `cancelled` reads as cancelled and reports its partial solution count
  separately.
- V6 `failure` reads as no proof found; an existential question renders `yes` or
  `no`, never an empty row set.
- V7 N>1 solutions render as one native radio group inside `<fieldset><legend>`
  with a single tab stop; N=1 renders the sole answer without a choice group;
  N=0 renders the terminal state alone.
- V8 Run, Cancel and Retry are native `<button type="button">` using native
  `disabled`: Run disabled with no selection and during a live run, Cancel
  enabled only during a live run.
- V9 Focus does not move on run start, completion or cancellation; when the
  control holding focus becomes disabled or absent, focus moves to Retry after an
  error and to Run otherwise.
- V10 The answer region carries `aria-busy="true"` while a run is live and
  `false` once it settles.
- V11 `axe.run` reports zero violations in every state, and every `incomplete`
  id except `color-contrast` is absent.
- V12 Rendered answer text comes from `serialized`, `solution.display[...]`, or a
  structural formatter over a decoded binding that emits only engine-authored
  tokens and falls back to `display` on any unrecognized shape. No binding is
  `JSON.stringify`ed; no corpus vocabulary is glossed; no Prolog syntax is
  assembled in JS. `humanizeGuidelineId` (u4) is the one such formatter — without
  it the four id-projecting questions render `write_canonical` bytes in every
  answer cell and radio label.

## Fixed public API

Declared here so a diff-blind suite compiles against the implementation.

```ts
// src/demo/DemoController.svelte.ts
export const DEMO_BUDGET: Readonly<BudgetSpec>; // frozen

/** The controller's whole view of the engine: one boot, one budgeted ask, one dispose. */
export interface DemoEngine {
  boot(): Promise<BootOutcome>;
  ask(id: unknown, budget: BudgetSpec, signal?: AbortSignal): Promise<AnswerResult>;
  dispose(): void;
}

export const createDemoEngine: () => DemoEngine; // EngineClient + AnswerService

/** `answer`, `limit` and `cancelled` carry rows; `failure`, `error` and `rejected` do not. */
export const solutionsOf: (result: AnswerResult) => readonly PlSolution[]; // `App` projects rows through it

export type DemoState =
  | { kind: 'booting' }
  | { kind: 'boot-error'; error: EngineError }
  | { kind: 'idle'; contract: EngineContract }
  | { kind: 'running'; id: QuestionId }
  | { kind: 'cancelling'; id: QuestionId }
  | { kind: 'settled'; id: QuestionId; result: AnswerResult };

export class DemoController {
  constructor(engine?: DemoEngine);
  state: DemoState;              // $state
  selected: QuestionId | null;   // $state
  solutionIndex: number;         // $state, -1 when no row is chosen
  select(id: QuestionId): void;
  run(): Promise<void>;
  cancel(): Promise<void>;
  retry(): Promise<void>;
  selectSolution(index: number): void;
  dispose(): void;
}
```

`cancelling` is transient: the terminal state is always `settled` carrying the
`AnswerResult`, so one value owns what the view renders. The cancel
acknowledgement never does — under a hard deadline or a reset it reports `false`
for a run that genuinely stopped (map S3, S4).

## Phase-1 rulings

`test-m1u6` raised eight readings the predicates did not decide. Rulings bind.

- **Q1 injection seam** — `App` takes `controller?: DemoController`, defaulting to
  a fresh one; `src/main.ts` builds the shipped instance. `App` must not know how
  to assemble an engine, and injecting the controller lets a test drive a state
  directly instead of scripting an engine round trip. `RunControls` and
  `AnswerPanel` take plain typed props plus callbacks and never see the controller.
- **Q2 run while booting** — a state-preserving no-op; Run stays disabled until
  `idle` or `settled`. Nothing queues invisibly.
- **Q3 illegal calls** — every disabled-state public call is a state-preserving
  no-op. The controller is a UI state machine, not a library boundary, and the
  view already prevents the call.
- **Q4 retry anchor** — `retry()` reruns `state.id`, never `selected`. Changing
  the selection is a separate action whose affordance is Run.
- **Q5 initial row** — a settled result carrying solutions sets `solutionIndex`
  to 0, so exactly one radio is checked; no solutions leaves it `-1`.
- **Q6 boot vs loading** — one `booting` state, one label. V3 above is the whole
  matrix.
- **Q7 retry visibility** — Retry renders only for `settled` with
  `result.kind === 'error'`. `limit` and `cancelled` re-run through Run, which is
  enabled and already carries the same id. `boot-error` has no Retry; boot
  recovery is out of scope and deferred to `.agent/polish.md`.
- **Q8 row reset** — every run resets `solutionIndex` to `-1` before dispatch;
  Q5 then sets 0. An out-of-range `selectSolution` is a no-op, never a clamp or
  a throw.
